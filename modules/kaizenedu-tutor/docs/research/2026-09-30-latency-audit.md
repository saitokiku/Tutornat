# Research: Latency audit of the shipped turn path (2026-09-30)

Produced by a research agent on 2026-09-30 for `docs/REPLAN.md`. Vendor pages were egress-blocked from the sandbox; every price and latency figure that is not measured in this repo is a secondary-source number and is marked unverified in the text. Nothing here is public copy.

## Summary

WHERE THE SECONDS GO (one hands-free voice turn, read from code; every provider figure except the model hop is an estimate or third-party and is labelled so)

t=0 learner stops speaking.
1. VAD end-of-speech wait: 600 ms fixed (`lib/tutor/voice/vad.ts:71` VAD_END_OF_SPEECH_LAG_MS, used as `redemptionMs` :310 and `hangoverMs` :112). The per-band `thinkingPauseMs` (700–1,500 ms, `kaizen.config.ts:46-73`) is computed server-side and put on the wire (`lib/tutor/wire.ts:337`) but NO client file reads it (grep over components/ and app/ returns nothing), so README.md:79's claim that it is live is false. Worse: `/api/tutor/vad/` does not exist (no route under app/, no public/vad/, no rewrite in next.config; `docs/TOOLING.md:324` says "copy to public/vad in a prebuild script", never done), so `createSileroVad` throws on asset fetch and `createVad` silently falls back to the RMS energy detector on a deprecated main-thread ScriptProcessorNode (`vad.ts:227-288`, 2048-sample buffers = 43 ms granularity at 48 kHz). Cost: 600–650 ms, plus energy-VAD misfires/false barge-ins.
2. Encode 16-bit 16 kHz WAV (`wav.ts:264`): 32 KB/s, a 5 s utterance = 160 KB. Upload estimate: 20–50 ms wifi, 130–260 ms LTE uplink (unverified).
3. POST /api/tutor/asr: `requirePrincipal` = 2 serial DB round trips (`lib/tutor/auth/principal.ts:37` then `:42`), one Promise.all round trip (`asr/route.ts:101`), whole-clip `gpt-4o-mini-transcribe` via AI SDK `experimental_transcribe` (non-streaming, `lib/audio/asr-providers.ts:406`, default model `lib/audio/constants.ts:1090`), then `await recordUsageLine` BEFORE the response (`asr/route.ts:159`) = 4th round trip on the critical path. Provider estimate 400–900 ms for a 3–6 s clip (unverified; docs blocked from here). DB: 4 RTs × 10–30 ms same-region, 80+ ms cross-region (region alignment unverified; `pg` Pool max 4 in `lib/tutor/db/client.ts:110`, new TCP+TLS per cold Vercel instance).
4. POST /api/tutor/turn before the model call: principal 2 RTs; `enforceRateLimits` daily count 1 RT (`turn/route.ts:72`, `guards/rate-limit.ts:250`); `startTurn` Promise.all 1 RT (`engine.ts:163`); `runTurn` Promise.all 1 RT (`engine.ts:231`); `buildTurnContext` Promise.all of 5 queries 1 RT (`context.ts:180`); bank-item Promise.all 1 RT when a check/diagnostic is due (`context.ts:207`). ≈6–7 round trips (the test `latency-turn.test.ts:68` only counts the 3 inside the engine). Estimate 70 ms (10 ms RT) to 500 ms (80 ms RT).
5. Model: Gemini 3 Flash preview, thinking minimal, temp 0.4, maxOutputTokens 1,400 (`llm-call.ts:377`). Measured in `docs/SPIKE-latency.md` (2026-09-05, sandbox proxy, free key): TTFT 660–674 ms p50, first sentence 774–781 ms p50, opener 30 chars p50 with OPENING_SENTENCE_RULE. Artificial Analysis lists 0.98 s TTFT for the non-reasoning variant (search snippet, unverified). Prompt measured today with `buildSystemPrompt`: static sections 20,283 chars for 9-12 (persona 2,622 / band 1,109 / subjects 2,382 / coach 1,601 / safety 2,051 / safety-9-12 925 / crisis 1,408 / disclosure 586 / whiteboard 5,018 / checks 2,563), 19,224 for 13-17; full WORK-turn prompt 21,326 chars ≈ 5.3k tokens (chars/4; no tokenizer in node_modules). The spike showed 118→2,453 tokens moved TTFT −71 ms, so prompt size is a cost/caching lever, not a first-token lever. Tag parser (`turn/tags.ts`) holds text while a `[[…]]` is open, so a turn that opens with `[[wb {"type":"wb_open"}]]` or `[[reaction …]]` delays the first sentence by ~15 tokens (~60–100 ms).
6. POST /api/tutor/tts per sentence, requested only when the `sentence` frame arrives (`turn-controller.ts:456-459`, prefetch 1 in `playback-queue.ts:103`): principal 2 RTs + Promise.all 1 RT (`tts/route.ts:308`), then `generateOpenAITTS` NON-streaming (`tts-providers.ts:282-302` awaits `response.arrayBuffer()`, default mp3, no `response_format`, no `stream_format`; provider-config only resolves key/model/baseUrl, `lib/server/provider-config.ts:696-770`), then `await recordUsageLine` before the bytes go out (`tts/route.ts:365`). Third-party numbers for gpt-4o-mini-tts: first chunk <500 ms, median time-to-first-speech 814 ms (search snippets, unverified); we wait for the whole clip, so estimate 700–1,200 ms for a 30-char opener.
7. Client: `response.arrayBuffer()` → `bytes.slice(0)` copy → `decodeAudioData` (mp3, 5–80 ms depending on device) → `source.start(0)` with a 5 ms ramp (`playback-queue.ts:328-363`); AudioContext 'interactive' output latency ~10–40 ms.
Serial estimate, wifi, same-region DB (10 ms): 600 + 30 + 60 + 600 + 70 + 770 + 40 + 900 + 60 ≈ 3.1 s from end of speech (≈2.5 s by the repo's own convention of subtracting the VAD wait). With a cross-region DB or LTE, 4–5 s. Budget is 1.5 s p50 / 3.0 s p90 (`kaizen.config.ts:168`). No real end-to-end number exists anywhere: `docs/SPIKE-latency.md` states TTS/ASR were never measured; `DATABASE_URL` is unset in `.env.local` (line 353 commented) and api.openai.com / elevenlabs.io / ai.google.dev are egress-blocked from this sandbox (WebFetch confirmed), so `pnpm latency --product` cannot run here either.

MOCK HARNESS (run today, then the two JSON files it wrote under docs/metrics/ were deleted so the tree is untouched): `pnpm latency --mock`: asr 254/260, llm_ttft 402/404, llm_first_sent 608/612, tts_first 304/306, first_audio 1,168/1,175 ms p50/p90. `pnpm latency --product --mock`: turn_to_audio 935/941, first_audio_pipelined 1,189/1,195, wb_action_to_sentence 177/179. These are the fake's configured delays (MOCK_ASR_MS=250 etc.) and prove only that the harness works.

FIVE BIGGEST WINS, in order (details and exact code changes in findings): 1) streaming ASR over a WebSocket during speech with provider endpointing (−900 to −1,400 ms); 2) stream TTS bytes and play the first chunk (−300 to −700 ms, also removes inter-sentence gaps); 3) cut 14 DB round trips on the first-audio path to ~6 and move ledger writes to `after()` (−100 to −600 ms depending on DB region); 4) start TTS from the turn stream server-side instead of a client round trip per sentence (−150 to −400 ms); 5) ship the Silero assets, wire the per-band pause, and start the model call eagerly at ~300 ms of silence (−100 to −300 ms typical). Also: Gemini implicit caching already applies to the 5k-token static prefix (≥1,024 tokens for Flash, 90% discount per Google's blog) provided the static sections stay first (they do) — this is cost, not latency. The free-tier key (owner: 5 RPM; third-party pages say 10 RPM for GA 3 Flash) cannot serve one session's cadence (turns + 20 s silence check-ins + grading/summary hops), let alone national scale; a paid tier and a GA model are prerequisites. The Gemini Live API (native audio, <500 ms claimed, server barge-in) would remove ASR+TTS entirely but forfeits the tag grammar that drives the whiteboard/checks and sends minors' audio to a second surface; evaluate on the harness before betting on it.

## Findings

### Win 1: stream ASR over a WebSocket while the learner is still talking (biggest win, est. -900 to -1,400 ms)

Effort: L (3-5 days incl. token route, invariant test update, phone testing)

Today the transcript cannot start until 600 ms of silence has passed, the whole 16-bit WAV has been encoded and uploaded, four DB round trips have run, and OpenAI has processed the entire clip in one shot. Streaming ASR sends PCM frames as they are captured, gets interim transcripts during speech, and uses the provider's own endpointing (OpenAI realtime `turn_detection: {type:'server_vad', silence_duration_ms: 300-500, prefix_padding_ms: 300}`; Deepgram Nova-3 `endpointing` + `utterance_end_ms`, sub-300 ms streaming latency claimed) so the final text is ready ~100-300 ms after end of speech instead of ~1.5-2 s. OpenAI realtime transcription supports gpt-4o-mini-transcribe over WebSocket per the Microsoft/OpenAI references (docs blocked from this sandbox; unverified first-hand). Exact change: (a) new route `app/(learner)/api/tutor/asr/token/route.ts` that runs the same guards as `asr/route.ts:101-145` once per session and mints an ephemeral provider token (OpenAI client_secrets, or a short-lived signed relay ticket if the provider has no ephemeral tokens) so no provider key reaches the browser (invariant e); (b) new `lib/tutor/voice/asr-stream.ts` that opens the WebSocket at session start, receives the 16 kHz Float32 frames from the VAD worklet (`vad.ts:322 onFrameProcessed` or a parallel AudioWorklet tap), converts to PCM16 and sends `input_audio_buffer.append`; (c) `turn-controller.ts` gains `submitTranscript(text, eosAt)` used on the provider's `...transcription.completed` event and keeps `submitVoiceAudio` as the fallback; (d) metering: seconds counted client-side per utterance and written by the token route's `after()` hook or by the turn route (engine writes a usage line already). Audio still never touches disk (invariant b) because frames go browser -> provider directly; put that in the no-audio-persistence test scan.

Recommendation: Build the WebSocket ASR path behind a feature flag with the multipart route as fallback; measure on a phone with `?metrics=1` (eosAt to asrAt) before and after; keep `silence_duration_ms` per band via the existing `thinking_pause_ms` setting.

Evidence: lib/tutor/voice/vad.ts:71,112,310 (600 ms wait); lib/tutor/voice/wav.ts:264 (16-bit WAV, 32 KB/s); lib/tutor/voice/asr-client.ts:196-208 (one multipart POST per utterance); app/(learner)/api/tutor/asr/route.ts:101,148,159 (4 DB round trips, whole-clip transcribe, ledger write awaited before the response); lib/audio/asr-providers.ts:406 (experimental_transcribe, non-streaming); docs/SPIKE-latency.md:3 (ASR never measured). External: https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/real-time-speech-transcription-with-gpt-4o-transcribe-and-gpt-4o-mini-transcribe/4410353 ; https://developers.deepgram.com/docs/understanding-end-of-speech-detection

### Win 2: stream TTS bytes and start playback on the first chunk; PCM instead of mp3 (est. -300 to -700 ms, and no gaps between sentences)

Effort: M (2-3 days incl. iOS Safari test of the worklet path)

`generateOpenAITTS` awaits the entire clip (`response.arrayBuffer()`), the route re-buffers it into a `Uint8Array` and sets `content-length`, and the client awaits the whole body then `decodeAudioData`s it. OpenAI's /audio/speech streams with chunked transfer and supports `response_format: 'pcm'` (24 kHz 16-bit) and, for gpt-4o-mini-tts, `stream_format: 'sse'|'audio'`; third-party measurements put the first chunk under ~500 ms while median full-clip time-to-first-speech is ~814 ms (unverified snippets). ElevenLabs Flash v2.5 (`/stream`, `output_format=pcm_16000`, ~75 ms model latency claimed) is the alternative and the key is already in .env.local. Exact change: (a) `lib/audio/tts-providers.ts` add `generateTTSStream(config, text, signal): Promise<{stream: ReadableStream<Uint8Array>, format}>` for openai-tts returning `response.body` with `response_format:'pcm'` (and elevenlabs `/stream`); (b) `tts/route.ts:353-394` return `new Response(stream, {headers:{'content-type':'audio/pcm; rate=24000'}})` without content-length; (c) `tts-client.ts` return `response.body` instead of `arrayBuffer()`; (d) `playback-queue.ts` `PlaybackSink` gains `startStream(reader, onFirstChunk, onEnded)`: an AudioWorklet ring buffer (or successive `AudioBufferSourceNode`s of ~100 ms PCM chunks scheduled at `nextStartTime` so sentences are gapless, instead of `source.start(0)` on `onended` at :142-165); `onFirstAudio` fires on the first chunk. Keep the current decode path for wav/mp3 fallbacks.

Recommendation: Do this before changing providers: it is one server function, one route change, and a sink method; then A/B openai pcm vs ElevenLabs Flash on the harness `tts_first` hop.

Evidence: lib/audio/tts-providers.ts:282-310 (no response_format/stream_format, arrayBuffer); app/(learner)/api/tutor/tts/route.ts:353,385-394 (whole-clip response, content-length); lib/tutor/voice/tts-client.ts:85 (arrayBuffer); lib/tutor/voice/playback-queue.ts:135-165,328-363 (decode whole clip; next sentence started only in onEnded, so each boundary costs an event-loop hop plus a 5 ms ramp, and any late fetch is audible silence). External: https://github.com/hrosspet/write-or-perish/issues/371 ; https://www.usesherlock.ai/blog/time-to-first-byte-voice-ai ; https://elevenlabs.io/docs/overview/models

### Win 3: cut the 14 database round trips on the first-audio path to ~6 and never await ledger writes before responding (est. -100 ms same-region to -600 ms cross-region)

Effort: S-M (1-2 days for a-c; +1 day for d)

Per voice turn the critical path pays: ASR route 4 RTs (principal 2 serial + guards 1 + `await recordUsageLine` 1), turn route 6-7 RTs (principal 2 + daily-hop count 1 + startTurn 1 + runTurn 1 + context 1 + bank items 0-1), TTS route 4 RTs (same shape as ASR). The repo's own tests cap the media routes at 4 and the engine at 3 to the first sentence, but nothing counts the route-level principal and rate-limit hops. Exact changes: (a) `principal.ts:37-51`: one query joining account_sessions -> accounts -> learners (spike doc already names this); saves 1 RT on all three routes; (b) `asr/route.ts:159` and `tts/route.ts:365`: wrap `recordUsageLine` in `after(() => ...)` from 'next/server' (stable since Next 15; this repo is on 16.2.11) so the bytes/transcript go out first; the ceiling still binds because the pre-flight sum is read before the provider call; (c) `turn/route.ts:72`: move `enforceRateLimits`'s daily count into the `startTurn` Promise.all (`engine.ts:163`) or the runTurn Promise.all (`engine.ts:231`); (d) TTS route: replace the per-sentence ownership + kill-switch + spend reads with an HMAC grant issued by the turn engine on each `sentence` frame (`{sessionId, turnId, index, exp}` signed with a server secret), verified in-process; keep only the ledger sum read; (e) confirm the Vercel function region and the Neon/Postgres region match (unverified; Neon reports single-digit ms same-region vs 200-300 ms cross-region). Also consider `@neondatabase/serverless` over HTTP for the one-shot guard queries on cold instances (TCP+TLS setup is ~8 RTs per new `pg` connection).

Recommendation: Ship (a)-(c) first (small, test-covered by extending the round-trip probes to the route level); then (d) with the streaming TTS change.

Evidence: lib/tutor/auth/principal.ts:37,42; app/(learner)/api/tutor/asr/route.ts:101,159; app/(learner)/api/tutor/tts/route.ts:308,365; app/(learner)/api/tutor/turn/route.ts:72; lib/tutor/turn/engine.ts:163,231; lib/tutor/turn/context.ts:180,207; lib/tutor/guards/rate-limit.ts:214-221,250; tests/tutor/latency.test.ts:189 (MAX_ROUND_TRIPS=4) and tests/tutor/latency-turn.test.ts:68 (3 to first sentence); lib/tutor/db/client.ts:110 (`new Pool({max:4})`); docs/SPIKE-latency.md:166-176. ### Win 4: start the first sentence's TTS from inside the turn stream instead of a client round trip per sentence (est. -150 to -400 ms)

Effort: M (2 days)

The client only learns a sentence exists when the SSE frame arrives, then issues a new HTTPS POST (cookie auth, JSON parse, 4 DB RTs) before any synthesis starts. The server knows the sentence ~one network hop earlier and already holds the principal, session, and spend totals. Exact change: in `engine.ts` `handle()` (:476-496), when the first `sentence` is produced, call `generateTTSStream` immediately and emit the audio as `audio_chunk` frames inside the same SSE stream (base64 is +33% bytes; at 24 kHz PCM that is ~64 KB/s, acceptable) or, on a single-process deploy (the Docker image; not per-route Vercel functions), park the provider stream in a per-process map keyed by turnId+index so the client's `/api/tutor/tts` call attaches to an already-running synthesis. The client `sse-client.ts` parses `audio_chunk` into the streaming sink; later sentences can keep the pull model. This also makes the whiteboard `action`-to-`sentence` timing tighter because audio and drawing come down one connection.

Recommendation: Do after Win 2 (it reuses `generateTTSStream`); keep the pull route for sentences 2..n and for replay.

Evidence: lib/tutor/turn/engine.ts:476-496 (sentence frames produced server-side); lib/tutor/voice/turn-controller.ts:456-459 and lib/tutor/voice/playback-queue.ts:167-190 (client requests audio only after the frame); components/tutor/session/use-tutor-session.ts:223-231 (per-sentence fetch); lib/tutor/turn/warm.ts:290-294 (per-route serverless functions do not share a process; warm-up does not carry).

### Win 5: the Silero VAD never loads, the per-band thinking pause is not wired, and end-of-speech is not adaptive (est. -100 to -300 ms typical; -900 ms for the 4-8 band once its 1,500 ms pause goes live)

Effort: S (assets + wiring: half a day) / M (eager turn: 1-2 days)

(1) `VAD_ASSET_PATH='/api/tutor/vad/'` but no such route, no `public/vad/`, no next.config rewrite exist, so `MicVAD.new` fails and `createVad` falls back to `createEnergyVad`: an RMS detector with an adaptive floor on a deprecated ScriptProcessorNode (main thread, 2048-sample frames), which also drives barge-in while the tutor speaks (`setProfile('speaking')` just raises the noise ratio 1.6x). Fix: prebuild script copying `node_modules/@ricky0123/vad-web/dist/{vad.worklet.bundle.min.js,silero_vad_v5.onnx}` and `node_modules/onnxruntime-web/dist/ort-wasm-simd-threaded.{mjs,wasm}` (14 MB; jsep variant is 27 MB, avoid) into `public/vad/`, set `assetBasePath='/vad/'`, and serve with `Cache-Control: public, max-age=31536000, immutable`; preload them on the 'Ready when you are' screen so the first hands-free utterance is not lost to model load. (2) `thinkingPauseMs` is delivered in `GetSessionResponse` (`wire.ts:337`) but never read; pass `initial.thinkingPauseMs` into `createVad` as `redemptionMs`/`hangoverMs` and into `createTurnController({endOfSpeechLagMs})` so the metric subtraction matches. (3) Make it adaptive: with streaming ASR, let the provider's `silence_duration_ms` be 300-500 ms and start the model turn eagerly on the first final transcript; if speech resumes within the band's pause, abort the in-flight turn (the controller already guards continuations by generation and the engine writes no row for a failed/aborted turn, `engine.ts:541`) and resubmit with the longer text. Without streaming ASR, at least end the wait early when the interim transcript ends in a terminator.

Recommendation: Ship the assets and the wiring this week (small, high-confidence); do the eager-turn behaviour together with Win 1.

Evidence: lib/tutor/voice/vad.ts:56,294-349 (asset path, Silero -> energy fallback); no matches for `api/tutor/vad` under app/ or public/ (grep, find); docs/TOOLING.md:324 (assets 'must be served', 'copy to public/vad in a prebuild script'); lib/tutor/wire.ts:337 vs zero client readers (grep components/ app/); README.md:79 (claims the per-band pause is live); components/tutor/session/use-tutor-session.ts:316-323 (createVad without redemptionMs), :244-257 (createTurnController without endOfSpeechLagMs); kaizen.config.ts:42-79.

### Prompt size and caching: 5.3k tokens per turn is a cost lever, not a first-token lever; Gemini implicit caching already applies if the prefix stays stable

Effort: S (logging: hours; trimming: 1 day with prompt lint)

Measured today: static sections 20,283 chars for 9-12 / 19,224 for 13-17, full WORK-turn prompt 21,326 chars (~5.3k tokens at 4 chars/token; whiteboard.md alone 5,018, subjects.md 2,382, checks.md 2,563). The spike found a 20x prompt-size increase moved Gemini TTFT by -71 ms, so trimming will not buy first-audio time. It does affect cost and cache hits: Google's implicit caching (2.5-generation and later per the Google blog; applies to 3.x per third-party pages, unverified) needs >=1,024 tokens of identical prefix for Flash and gives a 90% discount on cached tokens. `buildSystemPrompt` puts the static sections first and the changing context/turn sections last, and the message history follows the system prompt, so the prefix already qualifies; keep it that way (do not move `Phase/Minutes left` above the statics). If the live turn ever moves to Anthropic, caching is explicit (`cache_control` on the static block) and must be added in `lib/ai/llm.ts`. Trimming whiteboard.md's action catalogue to the types actually validated by `actions.ts` would cut ~1k tokens per turn at national scale.

Recommendation: Verify cache hits by logging `usageMetadata.cachedContentTokenCount` from the Gemini response in `settle()` (llm-call.ts:411-427); trim only for cost.

### Client-side: every text_delta re-renders the whole session screen; playback is not gapless; AudioContext resume is not ensured on the voice path

Effort: S (1 day)

(1) `set()` in the turn controller notifies subscribers on every `text_delta`, `sentence`, `usage`, and `updateMetrics`, and `useSyncExternalStore` returns the whole state object, so SessionScreen, TutorTile, BoardPane, Transcript (maps all entries) and Dock re-render 20-50 times a second while the model streams; the avatar rig runs its own rAF loop so it is not blocked, but on a mid-range phone this competes with decode and the (currently main-thread) energy VAD. Fix: coalesce `text_delta` into one `set()` per animation frame (or 50 ms), and split the store into slices (transcript / phase / metrics) with selector-based subscriptions. (2) `playback-queue` starts sentence N+1 in sentence N's `onended` callback with `source.start(0)`, so every boundary costs an event-loop turn plus a 5 ms ramp, and a late fetch is silence; with a 30-char opener (~1.5 s of audio) and sentence 2 needing 4 DB RTs plus full synthesis of ~100 chars, p90 gaps are likely. Fix: schedule with `source.start(nextStartTime)` where `nextStartTime = previousStart + previousDuration`, and raise `prefetch` to 2. (3) `ensureRunning()` is called for `submitText` but not on the VAD/PTT path; if iOS suspends the context (call, background), the first tutor sentence after resume is inaudible. Fix: call `ensureRunning()` in `startHead`/`onFirstAudio`. (4) `unlockAudio` and the mic request happen in `start()` before the greeting `checkIn()`, so the first audio also waits on the permission prompt; acceptable, but the greeting could be requested in parallel with `openMicrophone()`.

Recommendation: Batch deltas per frame and schedule gapless starts in the same PR; measure main-thread long tasks on a mid-range Android with the metrics overlay.

### Deploy topology: three separate serverless functions per turn each cold-start and reconnect to Postgres; warm-up never reaches the turn function

Effort: M (topology decision + 1-2 days)

`vercel.json` deploys every route as its own function (`maxDuration` 300 for app/api/**; the product routes under app/(learner)/api rely on per-route `maxDuration`). `warmTurnPathInBackground` runs in the session/guest function, which by its own comment cannot warm the turn function on a per-route deployment; the provider connection probe is opt-in and unmeasured. A first turn can therefore pay three cold starts plus three fresh `pg` TCP+TLS connections. Options: (a) run the voice routes on one long-lived process (the Docker image with `output: 'standalone'` on Fly/Railway/Cloud Run in the same region as the DB) so connections, prompt cache, and provider sockets stay warm; (b) on Vercel, keep the three routes in one function by exporting them from one handler file and turn on Fluid compute; (c) turn on `TUTOR_WARM_CONNECTION=1` where the handshake can be timed. Unverified: which Vercel region the project uses and where the database lives.

Recommendation: Measure cold vs warm turn on production with `?metrics=1` (firstDeltaAt-asrAt for the turn function) before choosing; if cold starts show up at p90, co-locate the three voice routes in one process.

### Alternative architecture to evaluate, not to adopt blind: speech-to-speech (Gemini Live API) removes ASR and TTS hops entirely

Effort: L (1-2 week spike)

Gemini Live (WebSocket, native-audio models, server-side VAD and an `interrupted` barge-in signal, <500 ms claimed by Google Cloud docs; snippets only, unverified) would collapse stages 2-7 into one stream and could meet 1.5 s p50 outright. Costs: the product's control grammar (`[[wb …]]`, `[[check …]]`, `[[hint]]`, `[[reaction …]]`) depends on text streaming through `tags.ts` before speech; Live returns audio first and transcripts second, so whiteboard and check timing would need tool-calling instead; the per-band persona/safety prompt and thinking-off routing would need re-validation on a different model family; minors' audio would flow to a second provider surface (minors-privacy review); a reported production issue on `gemini-live-2.5-flash-native-audio` streams silent audio on ~6% of calls. A cheaper middle path keeps the text LLM and replaces both edges with WebSockets (Wins 1 and 2), which preserves every invariant test that exists today.

Recommendation: Spike it on the harness only after Wins 1-3 are measured; if the streaming-edges path lands under 1.5 s p50 on a phone, speech-to-speech is not worth the control loss.
