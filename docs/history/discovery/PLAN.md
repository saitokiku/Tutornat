## Proposed sequence and approval gates

### 1. Reconstruct the work, with coverage visible

- Inventory each repository's docs, product decisions, tests, code, useful assets, issues, PRs, branches and relevant history. Locate existing local copies and check their status read-only so unpushed work is not silently missed.
- Read repo-specific AGENTS/CLAUDE files and relevant local skills before any execution. Treat claims in generated reports and PR summaries as claims to verify.
- Create a product timeline: what changed, which problem each attempt addressed, what was abandoned, and which decisions contradict one another.
- Pin review commits and keep a coverage ledger by repo and subsystem. Map the whole product; read critical paths deeply; disclose unreviewed areas rather than claiming every line was audited.
- Audit the existing consolidation against both source and destination code. Distinguish reusable ideas from compatible code and preserve provenance/licenses.

Output: one evidence map and a keep / repair / retire / unknown matrix, with file/commit references, user impact, and confidence. Include useful decisions from inactive attempts, not just the latest UI.

### 2. Establish technical and product evidence

- Read build/test commands and lifecycle scripts before running anything. Use separate disposable copies and synthetic data; preserve all original working trees.
- Check install reproducibility, available CI runs, existing unit/integration/browser tests, dependencies, production versus preview/mock behavior, core request paths and error handling.
- Classify checks as verified working, reproducibly broken, not tested, or blocked. List missing credentials/setup separately from code defects. Do not fix bugs during this pass.
- Evaluate voice/text sessions, interruption/recovery, whiteboard correctness, progress/evidence, persistence, privacy boundaries, accessibility, and cost controls in proportion to what exists.
- Paid model calls, production sessions, installs with material side effects, and tests needing live services get a separate scope/budget check before use. No private source or student data goes into public search queries or external indexing services. No private product work routes to DeepSeek; verify worker routing before dispatch.

Output: reproducible findings with exact commands, environments, commit IDs, logs/screenshots, and explicitly untested areas. Passing code tests do not establish learning efficacy.

### 3. Research the uncertain decisions, not everything about education

- Product: target learner, learner versus payer, triggering problem, alternatives already used, adoption friction, willingness to use/pay/fund, and a believable first distribution channel.
- Learning: tutoring versus answer provision, feedback/hints, retrieval/spacing, independent assessment and retention. Check whether fixed timing/repetition rules are supported for the intended learner/task rather than treating implementation constants as validated science.
- AI/engineering: current tutoring/voice/whiteboard approaches, available open-source components, reliability, latency, and per-session costs. Prefer primary sources and small reproducible probes over vendor claims.
- Risk: children's safety, consent, transcript handling, retention/deletion, account/tenant boundaries, accessibility, abuse of anonymous access, IP/licenses, and operator escalation. Legal questions require qualified review; an agent audit is not compliance certification.
- Reuse existing research only after checking its source, date, population/task, and relevance. Research claims must state the evidence type, limitations, and what decision they change.

Output: a short decision memo, cited evidence, conflicting results, and what NOT to build. Then return to the owner for the first substantive checkpoint: target user, core job, scope, success measure, and reuse/rebuild direction. Do not proceed to visual design merely because the audit finished.

### 4. Design the complete learning session before decorating screens

- Start from observed workflows and existing screens, components, tokens, copy and accessibility work. Do not assume the current visual language is either right or disposable.
- Map one complete learner journey: arrive with a need, start, attempt, receive help, check understanding, finish, and return. Include misunderstanding, interruption, microphone refusal, text-only use, slow/offline states, and provider failure.
- Propose three materially different interaction directions, not three color swaps: conservative reuse, strongest fit, and a divergent concept. Explain each tradeoff using the agreed learner and job.
- After direction approval, build a clickable prototype in isolation. Label simulated content clearly. Test keyboard, mobile/touch, readability and loading/error/empty states. Show the actual flow, not just a homepage.
- Validate with the owner and, with appropriate permission/consent, intended users. Agent walkthroughs are QA, not substitutes for real user research. Consolidate the chosen direction into one design system and component/state contract.

Output: selected flows, tested prototype, concise design spec, evidence from feedback, and unresolved questions. Owner approves the experience before production implementation.

### 5. Choose a foundation and plan a measurable pilot

- Compare improving KaizenEdu, selective extraction, and a fresh base only if evidence justifies it. Include maintenance burden, migration risk, license constraints, and what is genuinely reusable. Newest is not automatically best.
- Define the data model, key interfaces, permissions, failure behavior, cost limits, diagnostics, rollout/rollback, and acceptance tests for the selected scope.
- Build later in small complete user journeys with test-first changes, independent specification review, and independent quality/security review. No team concurrently edits overlapping files without explicit ownership.
- A pilot gate requires reproducible setup, working end-to-end sessions, truthful progress claims, safe failure/recovery, privacy/deletion and cost controls, accessible core flows, and operator visibility. Match exact thresholds to the approved scope rather than inventing them now.
- Learning/retention and demand are hypotheses until measured with real users. Avoid equating engagement, correct assisted answers, or AI-reviewer agreement with product success.

Output: one approved product brief, design/architecture decision record, prioritized build backlog, and pilot verification plan. Implementation and launch each need explicit approval.
