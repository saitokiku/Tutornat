## Defect 1 — stale learner-scoped notice covers another learner's phone screen (reproduced in evidence)

- **Independently executed (coordinator screenshot):** `learn-module-student-320.png` shows Bea's reset status still displayed while viewing a different learner's Learn page at 320px, overlapping content.
- **Source inspection (root cause):**
  - `ui.status` is one global slot (`app.js:15`), not keyed by learner, role or route.
  - `setStatus()` (`app.js:189-193`) auto-dismisses only `kind==='ok'` notices without an action and only when `!ui.undo`, after 6000 ms. Nothing dismisses a notice when `ui.learnerId` changes (`app.js:273`: `ui.learnerId = v; render();`) or when role changes (`app.js:271`).
  - `renderStatus()` (`app.js:194-202`) re-paints whatever is in `ui.status` on every render, so the notice follows the user across learners and routes until the timer fires or Close is pressed.
  - The reset confirm (`app.js:226`) emits `setStatus(t('reset_done',{name}),'ok')` — a learner-named notice — immediately before the harness switched role and learner (`shell.e2e.cjs:104-115`).
  - `#status` is `position:fixed` above the tab bar (`styles.css:192`); at ≤560px it stretches edge-to-edge (`styles.css:261`), so on a phone it physically covers the bottom of the work area, where K–2/3–5 primary controls sit.
- **Decision:** fix this as the first slice. Notices become **context-bound**: every notice records the `learnerId` (and role) it was raised for; a learner switch dismisses notices that belong to another learner (dropping their Undo the same way reset already drops a stale Retry at `app.js:224`); error notices with Retry keep today's `inContext(origin)` guard (`app.js:139`). Residual: an in-context notice still overlays content for up to 6 s on phones; it is closable. Whether phones should get an inline notice instead of a bottom toast is an owner taste question (Q2), **not** part of this slice.

Both are consistent with "swallowed right after an async completion, phone only".
- **Decision:** stays **open**. The Product Verifier must exercise it with **no retry** (single click, ≥10 iterations at 390px immediately after a completion) and preserve every red result. ## Defect 3 — "today" is the UTC calendar date, not the family's local date (observed by coordinator; cause located in source)

- **Coordinator observation (out-of-band, this consultation):** the shell screenshot header read "Friday October 2" while the host clock was Thursday Oct 1, 22:05 America/Chicago. The run's own `started` stamp is `2026-10-02T03:05:47Z` — the UTC date had already rolled over.
- **Source inspection (cause):** `demo-service.js:51-52` — `clock = () => new Date().toISOString()` and `todayFn = () => opts.today || clock().slice(0,10)` → the service's `today()` is the **UTC** date. `app.js:10` constructs `window.DemoService.createDemoService({})` with no `today`/`clock` option, so the default applies. Every consumer inherits it: Today header `fmtLong(today)` (`app.js:238`), week strip (`app.js:240,344`), parent/student Today, overdue (`task.due < today`, `app.js:334`, `learning-views.js:88`), Plan "this week" (`plan-view.js:71`), and Activity day headings, which group by `String(e.at).slice(0,10)` = UTC date of the timestamp (`learning-views.js:182`). Rendering of date-only strings with `timeZone:'UTC'` on `iso+'T00:00:00Z'` is itself correct; the wrong input is the day chosen.
- **Impact:** for a US family, from 7 pm CDT (6 pm CST, 5 pm PDT) the app says it is tomorrow, tasks due today read "was due", the week strip advances early, and evening work is filed under the next day. Parent-first product; evening is when parents look. Hypothesis-level, **not independently executed** with a fixed clock.
- **Decision:** include in the slice. Smallest fix is shell-side and core-frozen: pass a local-calendar `today` function at `app.js:10` (`createDemoService({ today: () => <local YYYY-MM-DD> })`); the `at` timestamps stay ISO instants. Activity day grouping (`learning-views.js:182`) and `C.fmtTime` (`copy.js:237`, not read) need the Verifier's timezone case first; the engineer touches `learning-views.js` only for a reproduced failure and documents it. The service already exposes `opts.today`/`opts.clock` for exactly this injection, so no `demo-service.js` edit is needed.
